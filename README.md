# ファンミーティング参加受付システム(モック版)

コミュニティイベントの申込受付・抽選・繰上・QR 受付を一気通貫で回すシステムのモックです。
顧客ヒアリングで要件を引き出すための「動く画面」であり、データモデル・状態遷移・
締切/選定/繰上ロジック・QR 照合は本実装でそのまま使える形で作ってあります。

仕様の正は [docs/mock-instructions.md](docs/mock-instructions.md)(開発指示書のスナップショット)。

## 業務フローと自動化方針(要約)

| # | 現行の運用 | 自動化 | 実装 |
|---|---|---|---|
| 1 | Google フォームを毎回作る | 自動化 | イベント登録で申込フォームが自動で生える(内蔵フォーム・入力はメールアドレスのみ) |
| 2 | チャットで告知 | 半自動化 | 告知文を自動生成し、コピーして手動投稿 |
| 3 | 定員超過を目視 | 自動化 | 申込上限到達・締切日時で自動締切。手動締切ボタンもあり |
| 4 | 確定連絡を手作業 | 自動化 | 選定(先着/抽選)と当選者への一括メール通知。待機・落選者は申込状況ページで確認 |
| 5 | キャンセル時の繰上連絡 | 半自動化 | 当選者の行で「キャンセル」→ 確認ダイアログ(繰上先を表示)→ 承認で無効化・繰上・通知が一括実行 |
| 6 | 紙の名簿で受付 | 自動化 | QR チケットをスマホでスキャン、無効なら入場ブロック |

## 技術構成

- Next.js (App Router) / TypeScript
- Postgres(Supabase 想定。ローカル Postgres でも可)
- Resend(繰上当選メール。API キー未設定時はコンソール出力にフォールバック)
- `qrcode`(QR 生成)/ `html5-qrcode`(スマホブラウザで読取)
- ホスティング: Vercel

認証と通知は差し替え前提のアダプタ構造:

- 認証: [src/lib/auth/provider.ts](src/lib/auth/provider.ts) / [src/lib/auth/fansCode.ts](src/lib/auth/fansCode.ts)
- 通知: [src/lib/notify/channel.ts](src/lib/notify/channel.ts)(モックはメール → 別チャネルはここに追加)

## 認証モード(AUTH_MODE)

対象コミュニティ基盤は Fans'(https://www.fansnet.jp/ ロココ株式会社)。
**Fans' は第三者向けの公開 API / OAuth / SSO を提供していない**(2026-09 調査)ため、
「Fans' アカウントでログイン」は直接実装できない。代わりに2モードを用意:

| モード | 用途 | ログイン方法 |
|---|---|---|
| `mock`(既定) | 開発・デモ | シード会員から選んでワンクリック |
| `fans_code` | 本番運用 | メール + **参加コード** → 確認リンクをメール送信 → クリックでログイン |

fans_code の会員判定は **「会員名簿 または 参加コード」**(管理画面 `/admin/settings` から
運営者が設定・再デプロイ不要)。どちらか一方だけの運用でもよい:

1. **会員名簿**: Fans' 管理画面からエクスポートした会員CSVを取り込むと、名簿にある
   メールアドレスは**コード入力なしで**ログインできる。CSVの表示名は初回ログイン時の
   表示名として自動採用。取り込むたび洗い替え。
2. **参加コード**: 管理画面で自動生成または手入力し、**Fans' の会員限定投稿で告知**する
   (投稿用の文面も自動生成・コピー可)。コードを見られるのは課金会員のみなので、
   「コードを知っている = Fans' 会員」という判定を Fans' のペイウォールに委ねる。
   名簿を使わない運用と、名簿取り込み後に増えた新会員の救済に使う。
   退会者対策はコードの定期変更(即時反映)。

運営者(role=admin)は名簿・コードとも免除(締め出し防止)。

運営者は事前に `members.role='admin'` の行を自分のメールアドレスで作っておくと、
同じフロー(メール+コード)で管理画面に入れる。

切替: 環境変数 `AUTH_MODE=fans_code` を設定して再デプロイ(コード・名簿はDB管理のため
以後の変更に再デプロイ不要)。`FANS_JOIN_CODE` 環境変数は初期ブートストラップ用の
フォールバック(DB未設定時のみ有効)。

## セットアップ

```bash
npm install
```

`.env.example` をコピーして `.env` を作成し、値を設定する:

```bash
cp .env.example .env
```

- `DATABASE_URL`: Postgres 接続文字列(Supabase は Project Settings > Database > Connection string)
- `RESEND_API_KEY`: 未設定でも動く(メールはコンソール出力になり、通知履歴には記録される)

スキーマ適用とシード投入:

```bash
npm run db:setup
```

```bash
npm run db:seed
```

シード内容: 運営者1名 + 会員10名、イベント2件(抽選型に申込8件 / 先着型に申込3件)。
すぐデモできる状態になります。

開発サーバー起動:

```bash
npm run dev
```

http://localhost:3000/login で「運営 太郎」を選ぶと管理画面、会員を選ぶと申込画面に入れます。

## Vercel へのデプロイ

1. このリポジトリを Vercel にインポート
2. 環境変数を設定: `DATABASE_URL`(Supabase の Transaction Pooler 推奨)、`DATABASE_SSL=true`、`AUTH_SECRET`(ランダム値)、`APP_URL`(本番 URL)、`RESEND_API_KEY`、`MAIL_FROM`
3. デプロイ後、ローカルから本番 DB に向けて `npm run db:setup && npm run db:seed`

## デモシナリオ(ヒアリング当日)

1. 管理画面でイベント作成 → 申込ページが即座に生える
2. 告知文をコピー
3. 会員としてログインして申込 → 残り枠が減る → 上限到達で自動締切。別イベントで手動締切も見せる
4. 選定実行 → 当選者にのみメール。待機者でログインし「待機中」表示を確認
5. 当選者のチケット(QR)を開く
6. 当選者を「キャンセル」→ ダイアログに繰上先が表示 → 承認 → 待機1位が当選、メールが届く
7. 受付画面で QR を読む → 緑。もう一度 → 赤「入場済み」。キャンセル者の QR → 赤「キャンセル済み」
