## 1. なぜモックを先に作るか

顧客はITに詳しくないコミュニティ運営者。文書で要件を聞いても「いい感じにしてほしい」以上の答えは返ってこない。**動く画面を触ってもらい、その反応から要件を引き出す。** モックはヒアリングの道具であり、完成品ではない。

したがって、モックに求めるのは「6つの業務フローが画面上で一周すること」。裏側が本物である必要はない。ただし、後で本物に差し替えるときに作り直しにならない構造にすること。

## 3. 業務フローと自動化方針

顧客の現行運用6ステップに対する自動化方針。**この表が要件の正。** 迷ったらここに戻る。

| # | 現行の運用 | 自動化レベル | モックでの実装 |
|---|---|---|---|
| 1 | Googleフォームを毎回作る | **自動化** | イベントを登録すると申込フォームが自動で生える。サービス内蔵のフォームと回答DBを使い、外部サービスに個人情報を出さない |
| 2 | チャットで告知しURLを貼る | **半自動化** | 告知文を自動生成しコピーボタンを置く。投稿は運営者が手動 |
| 3 | 定員超過をスプレッドシートで目視 | **自動化** | 申込数が閾値に達したら募集を自動で締め切る。運営者が任意のタイミングで手動で締め切ることもできる |
| 4 | 確定連絡を1人ずつ手作業 | **自動化** | 参加者選定と当選者への通知を一括で実行。待機者・落選者にはメールを送らず、自分の申込状況画面で確認してもらう |
| 5 | キャンセル時に夜中に繰上連絡 | **半自動化** | 運営者がキャンセル者の行で「キャンセル」を押し、確認ダイアログで承認する(2重確認)。承認と同時にチケット無効化・待機1位の繰上・繰上当選通知が自動実行 |
| 6 | 紙の名簿で受付 | **自動化** | 当選者にQRチケットを配布。受付でスキャンし、無効なら入場をブロック |

### #1 の補足:なぜ自社フォームか

Googleフォームを外した理由は情報漏洩リスク。ただし自社DBに置いても漏洩リスクはゼロにならない。**集める情報を最小限にすること**が本当の対策。

**申込フォームで入力させるのはメールアドレスのみ(決定済み)。** 表示名はログインしたコミュニティアカウントから取得し、入力させない。本名・住所・電話番号は集めない。メールアドレスは通知の送信先として使う。

### #3 の補足:閾値の定義

イベントに `capacity`(定員)と `application_limit`(申込受付上限)の2つを持たせる。

- `application_limit = capacity` → 先着順。定員に達した時点で締切、全員当選
- `application_limit > capacity` → 抽選。上限に達した時点で締切、定員分を抽選で当選、残りは待機

顧客の「閾値で募集終了」と「参加者選定」の両方をこの2値で表現できる。どちらの運用かはヒアリングで決めるので、モックは両方動くこと。

締切は自動と手動の2通り。上限到達か締切日時で自動的に閉じるほか、運営者が「募集を締め切る」ボタンで任意に閉じられる。上限に満たなくても告知の反応を見て早めに閉じたい、という運用に対応するため。手動締切は確認ダイアログを1回挟む。

### #4 の補足:通知は当選者にだけ送る

選定結果のメールは当選者にのみ送る。待機者・落選者には送らない。落選メールは受け取る側の気分がよくないうえ、待機者はその後繰り上がればそのとき当選メールが届く。

その代わり、待機者・落選者が自分の状況を知る手段は「自分の申込状況」画面だけになる。**告知文と申込完了画面に「結果は申込状況ページで確認できます」と必ず入れること。** これがないと「連絡が来ないんですが」という問い合わせが運営者に集中する。

### #5 の補足:人数入力ではなく、1人ずつワンクリック

顧客の当初要望は「キャンセル人数を選択」だが、**人数だけ入力する方式は採用しない。** キャンセルした人を特定しないと、その人のQRチケットが有効なまま残る。結果、定員オーバーと「キャンセルしたはずの人が入場できる」穴が同時に開く。

採用する操作は **ワンクリック + 確認ダイアログ1回(2重確認)**。

1. 申込一覧の当選者の行にある「キャンセル」を押す
2. 確認ダイアログが開く。誰をキャンセルし、誰が繰り上がるかを表示する
3. 承認すると、キャンセル・チケット無効化・繰上・通知が一括で走る。繰上当選通知は**申込フォームで入力されたメールアドレス**に自動送信する

**キャンセル1件ごとに繰上1件が自動で連動する。** 人数のまとめ入力より操作は単純で、処理も1件ずつ完結するため中途半端な状態が残らない。ダイアログで繰上先を見せるのは、2重確認を形式的なものにしないため。「本当に消しますか?」ではなく「この人が繰り上がりますが、よいですか?」と聞く。

## 4. モックの境界:何を本物にし、何を仮にするか

### 本物として実装する(後で作り直さない)

- データモデルと状態遷移
- 申込フォームと回答DB
- 閾値による自動締切(DBトランザクション内で判定。画面側のチェックだけでは連打で抜ける)
- 選定ロジック(先着・抽選)
- 繰上ロジック(排他制御込み)
- QRチケットの発行・読取・照合
- 繰上当選メールの送信(Resend)。繰上連絡の自動化はこの案件の中核なので、モックでも本物のメールを飛ばす
- 管理画面の一連の操作

### 仮で実装する(差し替え前提)

| 項目 | モックでの仮実装 | 本実装 |
|---|---|---|
| 会員認証 | シードした会員一覧から会員IDを選んでログイン(パスワードなし) | コミュニティ基盤のOAuth(ヒアリングQ1で決定) |
| 通知チャネル | メール(Resend)。全通知を `notifications` にも記録 | 同左。別チャネルの要望があればアダプタで追加 |

**差し替えを前提に、認証と通知はアダプタとして切り出すこと。** `auth/provider.ts` と `notify/channel.ts` の2ファイルを差し替えれば済む構造にする。メール送信が失敗してもDB更新はロールバックせず、`notifications` に失敗を記録して管理画面に表示する。

### 作らない

- 決済、座席指定、物販
- コミュニティ本体の会員管理
- 参加者による自己キャンセル(顧客の要望は運営者主導のため。ヒアリング次第で追加)
- カスタム質問項目(イベントごとに質問を変える機能。まずは固定項目で)

## 6. データモデル

仕様書の内容を正とする。モック用の差分のみ記載。

```
members        id, display_name, email, is_active
events         id, title, starts_at, venue, capacity, application_limit,
               closes_at, status(draft|open|closed|selected|finished)
applications   id, event_id, member_id, status, waitlist_order, applied_at
               UNIQUE(event_id, member_id)
tickets        id, application_id(UNIQUE), token, checked_in_at
notifications  id, member_id, event_id, kind, body, sent_at
```

申込ステータス: `applied → won | waitlisted → (繰上) won → checked_in`、`won → cancelled`、`waitlisted → lost`

## 8. 受け入れ条件

モック完成の定義。すべて満たしてから顧客に見せる。

### F1 イベント作成 → フォーム自動生成

- 管理画面からイベントを作ると、会員向けの申込ページが即座に開ける
- 申込フォームの入力項目はメールアドレスのみ。表示名はログインアカウントから自動で入る
- Googleフォームや外部サービスを一切経由しない

### F2 告知文生成

- イベント管理画面に告知文(イベント名・日時・会場・申込URL・締切・「結果は申込状況ページで確認」の案内)が表示される
- ワンクリックでクリップボードにコピーできる

### F3 閾値による自動締切

- 申込数が `application_limit` に達した瞬間、イベントが `closed` になる
- 同時に複数の申込が来ても上限を超えない(並列リクエストでテストすること)
- `closes_at` を過ぎても締切になる
- 運営者が「募集を締め切る」を押すと、確認ダイアログ1回を経て即座に `closed` になる
- 手動締切後の挙動は自動締切と同じ(選定実行が可能になる)
- 締切後は申込ボタンが押せず、URLを直接叩いても弾かれる

### F4 選定・確定通知

- 「選定を実行」で、先着なら全員当選、抽選なら `capacity` 人が当選し残りが待機
- 実行と同時に当選者にのみ当選メールが送信され、通知履歴に記録される
- 待機者・落選者にはメールが送られない。自分の申込状況画面で「待機中」「落選」を確認できる
- 申込完了画面に「結果は申込状況ページで確認できます」と表示される
- 当選者にはチケットが発行される
- 選定は1イベント1回のみ。二重実行できない

### F5 キャンセルと繰上

- 申込一覧の当選者の行に「キャンセル」ボタンがある(1クリック)
- 押すと確認ダイアログが開き、キャンセルする人の表示名と、繰り上がる待機1位の表示名が表示される(2重確認)
- 待機リストが空、または繰上締切を過ぎている場合は、ダイアログに「繰上なし」と表示される
- 承認すると1トランザクションで実行される: ステータスを `cancelled` に変更、チケット無効化、待機1位を `won` に変更、チケット発行、繰上当選通知の記録
- 繰上当選者の申込時メールアドレスに、当選メールが実際に届く(チケットURL入り)
- 2件連続でキャンセルしても繰上は1件ずつ行われ、同じ人が2回繰り上がらない
- キャンセルしなければ何も変わらない
- 承認後、画面を再読み込みせずに一覧と通知履歴が更新される
- 無効化したチケットのQRを受付で読むと「キャンセル済み」で拒否される

### F6 QR受付

- チケットのQRをスマホで読み取り、1秒以内に合否が表示される
- 合格: 緑の全画面、表示名を大きく表示
- 不合格: 赤の全画面、理由を表示(無効なチケット / 別イベント / キャンセル済み / 入場済み+初回入場時刻)
- 同じQRを2回読むと2回目は「入場済み」で拒否される
- QRが読めない場合の手動検索(表示名)がある

### 全体

- 本番URLで上記すべてが動く
- シードデータで「会員10名、イベント1件、申込8件」の状態から即デモできる

## 9. デモシナリオ

ヒアリング当日に顧客へ見せる順番。この順で通しで動くことを最終確認する。

1. 管理画面でイベントを作成 → 申込ページが生えるのを見せる(#1)
2. 告知文をコピー(#2)
3. 会員としてログインし申込 → 残り枠が減る。上限に達して締切になる。別イベントで手動締切ボタンも見せる(#3)
4. 管理画面で選定実行 → 当選・待機が決まり、当選者にだけメールが飛ぶ。待機者としてログインし「待機中」表示を見せる(#4)
5. 当選者としてチケットを開く → QRが出る
6. 管理画面で当選者の「キャンセル」を押す → ダイアログに繰上先が出る → 承認 → 待機1位が当選に変わり、その人のメールに当選メールが届く(#5)
7. 受付画面でQRを読む → 緑。もう一度読む → 赤「入場済み」。キャンセル者のQRを読む → 赤(#6)

7で「なりすましが弾かれる瞬間」を見せるのが、このデモの山場。

## 10. セキュリティの最低ライン

モックでも守ること。後から入れると漏れる。

- 全ての判定(締切、権限、チケット照合)はサーバー側で行う。画面を隠すだけの制御にしない
- QRトークンは推測不能なランダム値(連番・UUID v1 不可)
- 管理画面は運営者ロールのみ。会員が `/admin` を叩いても弾く
- フォームで収集する個人情報はメールアドレスのみ。それ以外の入力項目を勝手に足さない
