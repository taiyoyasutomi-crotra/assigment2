### 設計判断(採用)

| 判断 | 理由 |
|---|---|
| DB アクセスは `pg` + 生 SQL(ORM なし) | 締切・選定・繰上で `SELECT ... FOR UPDATE` による行ロックを明示的に制御するため。ORM のトランザクション抽象を挟むより意図が読める |
| 申込の上限判定はイベント行の `FOR UPDATE` で直列化 | 指示書「画面側のチェックだけでは連打で抜ける」への対応。同時申込でも上限を超えない(F3) |
| キャンセル処理はイベント行 → 申込行の順にロック | 申込処理とロック順を揃えてデッドロックを回避 |
| 通知は「記録(トランザクション内)」と「配送(コミット後)」を分離 | 指示書「メール送信が失敗しても DB 更新はロールバックしない」。失敗は `notifications.status='failed'` として管理画面に表示 |
| `applications.email` カラムを追加(指示書のモデルへの差分) | 「繰上当選通知は申込フォームで入力されたメールアドレスに送信」を満たすため。会員マスタのメールと申込時の連絡先は別物 |
| `members.role` カラムを追加(差分) | 管理画面のサーバー側権限判定に必要。本実装ではコミュニティ基盤の権限に差し替え(TODO(hearing:Q1)) |
| `tickets.revoked_at` カラムを追加(差分) | キャンセル済み QR を受付で「キャンセル済み」として明示的に弾くため(F5/F6)。行削除だと「無効なチケット」としか出せない |
| 待機者の「落選」表示は繰上締切(開始2時間前)経過で切り替え | `lost` への状態更新バッチを持たずに指示書の表示要件(待機中→落選)を満たす。締切時刻は TODO(hearing:Q7) |
| QR トークンは `crypto.randomBytes(24)` の base64url | 指示書 10 章(連番・UUIDv1 不可) |
| 抽選は `crypto.randomInt` の Fisher–Yates | `Math.random` より抽選の公平性の説明がしやすい |

### 設計判断(棄却)

| 棄却した案 | 理由 |
|---|---|
| Supabase JS クライアント(supabase-js)での DB アクセス | クライアント経由ではマルチステートメントのトランザクション・行ロックが組めず、F3/F5 の排他制御が保証できない。Postgres 直結(接続文字列)に変更 |
| キャンセルの「人数入力」方式 | 指示書 3 章 #5 で明示的に棄却済み(チケット無効化の穴が開く) |
| 落選者への結果メール送信 | 指示書 3 章 #4 で明示的に棄却済み(当選者のみに送る) |
| ORM(Prisma / Drizzle)導入 | モックの規模に対してセットアップコストが見合わず、生 SQL の方がロック制御が明確 |
| 参加者による自己キャンセル | 指示書 4 章「作らない」に明記。ヒアリング次第で追加 |

### Fans'(fansnet.jp)連携の調査と fans_code 認証の実装

顧客のコミュニティ基盤は Fans'(ロココ株式会社のファンクラブプラットフォーム、X/Twitter連携型)。

**調査結果(2026-09-01)**: 公式サイト・ヘルプに第三者向けの公開 API / OAuth / SSO の記載なし。
「Fans' アカウントでログイン」の直接実装は現状不可能。

**採用した代替案(fans_code モード)**: 参加コード + メール確認リンク(マジックリンク)。
- 運営者が Fans' の**会員限定投稿**で参加コードを告知 → コードを見られるのは課金会員のみ
  → 「コードを知っている = 会員」の判定を Fans' のペイウォールに委ねる
- ログイン: メール + 参加コード → 15分有効・ワンタイムの確認リンクをメール送信 → クリックで登録/ログイン
- トークンは SHA-256 ハッシュで保存、参加コード照合は timingSafeEqual
- `AUTH_MODE=mock|fans_code` で切替(デモは mock、本番運用で fans_code)

**棄却した案**:
- X(Twitter) OAuth ログイン: Fans' 会員 ≠ X フォロワーであり、X アカウントと Fans' 会員資格の
  突合には結局 Fans' 側のデータが必要。X Developer 登録の運用負担も増える。ヒアリングで
  「会員名簿のエクスポート可否」を確認してから再検討(→質問リストへ)
- スクレイピングによる会員判定: 利用規約リスク。不採用

**制約(ヒアリングで説明)**: API がないため表示名の自動取得は不可(初回に自己申告)。
退会者は参加コードのローテーション + `is_active=false` で対応(運用ルールは Q2 で確認)。

検証済み: 誤コード拒否 / 正コードでリンク送信 / リンクでの新規登録・ログイン / リンクの再利用拒否。

**追加改善(同日、ユーザーフィードバック反映)**:
- 参加コードを環境変数から **DB 管理(`app_settings`)に変更**。管理画面 `/admin/settings` で
  自動生成(紛らわしい文字を除いた `FANS-XXXX-XXXX` 形式)または手入力でき、再デプロイ不要で即時反映。
  Fans' の会員限定投稿にそのまま貼れる告知文の生成・コピーも同画面に配置
- Fans' 管理画面から**会員CSVのエクスポートが可能**と確認できたため、名簿照合(`member_allowlist`)を追加。
  設計方針: 「つどCSVを読み込むのは面倒」というフィードバックに合わせ、**名簿は任意の強化オプション**とした。
  名簿が空ならコードのみで判定(CSV運用ゼロでも回る)。取り込むと「コード+名簿照合」になり、
  CSVの表示名を初回登録の表示名として自動採用(表示名の自己申告問題も解消)。列構成は自動判定、洗い替え方式
- 運営者(role=admin)は名簿照合を免除(名簿取り込みで運営者自身が締め出されるのを防止)
- 検証済み: コード自動生成・手動設定 / CSV取込(ヘッダ行スキップ・表示名採用)/ 名簿外メール拒否 /
  名簿内メールのログインと表示名引き継ぎ / 運営者免除
- 将来の自動同期(CSV不要化)はベンダー API 提供が前提のため、ロココ社への問い合わせ項目とする
- **判定ルールの再設計(同日、「コードいらなくね」フィードバック反映)**: 「コード AND 名簿」から
  **「名簿 OR コード」**に変更。名簿に載っているメールはコード不要(名簿だけで会員判定が成立するため、
  コードの併用は冗長)。コードは①名簿を使わない運用、②名簿取り込み後に増えた新会員の救済、の2用途に整理。
  ログイン画面のコード欄は任意入力に変更。検証済み: 名簿会員のコードなしログイン / 名簿外+正コード /
  名簿外+誤コードの拒否
