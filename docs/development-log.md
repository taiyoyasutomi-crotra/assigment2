### 設計判断(採用)

| 判断 | 理由 |
|---|---|
| DB アクセスは `pg` + 生 SQL(ORM なし) | 締切・選定・繰上で `SELECT ... FOR UPDATE` による行ロックを明示的に制御するため。ORM のトランザクション抽象を挟むより意図が読める |
| 申込の上限判定はイベント行の `FOR UPDATE` で直列化 | 指示書「画面側のチェックだけでは連打で抜ける」への対応。同時申込でも上限を超えない(F3) |
| キャンセル処理はイベント行 → 申込行の順にロック | 申込処理とロック順を揃えてデッドロックを回避 |
| 通知は「記録(トランザクション内)」と「配送(コミット後)」を分離 | 指示書「メール送信が失敗しても DB 更新はロールバックしない」。失敗は `notifications.status='failed'` として管理画面に表示 |
| `applications.email` カラムを追加(指示書のモデルへの差分) | 「繰上当選通知は申込フォームで入力されたメールアドレスに送信」を満たすため。会員マスタのメールと申込時の連絡先は別物 |
| `members.role` カラムを追加(差分) | 管理画面のサーバー側権限判定に必要。本実装ではコミュニティ基盤の権限に差し替え(TODO(hearing:Q1)) |
| `tickets.revoked_at` カラムを追加(差分) | キャンセル済み QR を受付で「キャンセル済み」として明示的に弾くため(F5/F6)。行削除だと「無効なチケット」としか出せない |
| 待機者の「落選」表示は繰上締切(開始2時間前)経過で切り替え | `lost` への状態更新バッチを持たずに指示書の表示要件(待機中→落選)を満たす。締切時刻は TODO(hearing:Q7) |
| QR トークンは `crypto.randomBytes(24)` の base64url | 指示書 10 章(連番・UUIDv1 不可) |
| 抽選は `crypto.randomInt` の Fisher–Yates | `Math.random` より抽選の公平性の説明がしやすい |

### 設計判断(棄却)

| 棄却した案 | 理由 |
|---|---|
| Supabase JS クライアント(supabase-js)での DB アクセス | クライアント経由ではマルチステートメントのトランザクション・行ロックが組めず、F3/F5 の排他制御が保証できない。Postgres 直結(接続文字列)に変更 |
| キャンセルの「人数入力」方式 | 指示書 3 章 #5 で明示的に棄却済み(チケット無効化の穴が開く) |
| 落選者への結果メール送信 | 指示書 3 章 #4 で明示的に棄却済み(当選者のみに送る) |
| ORM(Prisma / Drizzle)導入 | モックの規模に対してセットアップコストが見合わず、生 SQL の方がロック制御が明確 |
| 参加者による自己キャンセル | 指示書 4 章「作らない」に明記。ヒアリング次第で追加 |
